# W9 Platform subscription sandbox

Sandbox Checkout and the billing portal use the Stripe account for Crecy subscriptions. Use an independent billing account and dedicated restricted test key, signing secret, Price objects, portal configuration, and endpoint. Operator rent remains on its existing Stripe Connect integration. The founder-approved localized amounts, caps, and 30-day no-card Growth trial are defined in [the pricing and entitlements spec](./11_PRICING_ENTITLEMENTS_AND_BILLING_SPEC.md).

The screen lives at `/settings/billing`. Checkout, plan upgrade, and portal requests require the current operator origin, a signed-in AAL2 session, and active owner or unscoped administrator access to the selected workspace. A stale workspace form receives a conflict. The read projection contains the local plan, billing status, relevant dates, and action availability. Stripe identifiers stay in private persistence.

## Configure a disposable sandbox

1. Leave `CRECY_SAAS_BILLING_MODE` unset until an authorized sandbox is ready. With `sandbox` mode, configure the independent `CRECY_SAAS_STRIPE_*` values documented in `.env.example`. Point `CRECY_SAAS_SANDBOX_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_URL` at the same dedicated test project or local Supabase URL. Use a restricted `rk_test_` key with account and Price read, Subscription read and write, Invoice read, Checkout Session, and billing portal permissions limited to the operations in this slice. Set the actual rent account ID in `CRECY_RENT_STRIPE_ACCOUNT_ID` when both integrations are configured.
2. Create one fixed recurring Stripe Price per exposed `country.plan.interval` option. Keep the currency and minor-unit value equal to the approved book. Checkout validates the selected Price in Stripe and disables Adaptive Pricing. Keep each URL on the sandbox operator origin configured in `NEXT_PUBLIC_SITE_URL`.
3. Use an explicit test billing portal configuration with invoice history and payment-method updates enabled, plan updates disabled, and cancellation at the end of the period. Use that configuration’s ID in `CRECY_SAAS_STRIPE_PORTAL_CONFIGURATION`.
4. Set a Stripe account webhook using snapshot payloads and the SDK-pinned `2026-06-24.dahlia` event version at `/api/internal/providers/stripe-billing/webhook`. Subscribe to `checkout.session.completed`, `checkout.session.expired`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `customer.subscription.paused`, `customer.subscription.resumed`, `customer.subscription.pending_update_applied`, `customer.subscription.pending_update_expired`, `invoice.paid`, and `invoice.payment_failed`. Use a Stripe endpoint secret assigned only to this webhook. Vercel production rejects sandbox enablement.

Stripe subscriptions are initiated through hosted Checkout. A durable reservation produces the same idempotency key when an acknowledgment is lost. If Crecy still lacks a Stripe Session ID after 20 hours, it pauses the attempt for reconciliation to stay inside Stripe’s 24-hour key retention minimum. The Checkout return path displays the local state. Only an authenticated Stripe event followed by a fresh, correctly bound Subscription and paid-invoice snapshot can promote the paid entitlement. Processing the same event twice produces one projection and audit/outbox record. Superseded snapshots retry and re-read the current Stripe state.

The database prevents new or reactivated properties and units once an explicit trial deadline has passed or the subscription is restricted. Historical owner entitlements that explicitly allow restricted reads remain available. Resident payments, existing-data access, archiving, and security recovery retain their existing entry points. The daily operational sweep records one sample of active units per tenant billing date for organizations with a paid sandbox subscription in the configured Stripe account. It preserves earlier usage history and reports a retryable backlog if the bounded batch is full. Samples never create provider charges or reconstruct missed dates.

An owner or unscoped administrator can explicitly choose Free during or after a Growth trial after MFA. That restores eligible operations when the workspace has at most one active unit and one occupied staff seat and has no open checkout, Stripe customer, current or historical Subscription, or legacy provider references. A verified expired checkout with no Subscription can release the hold. Free conversion retains the original trial date, enforces the selected plan’s unit and staff caps, and writes one audit and outbox record. It makes no provider calls and is also available when the Stripe sandbox is disabled.

An active paid workspace can request a higher plan in its current currency and billing interval after explicitly confirming proration. The subscription must be current, have one item, and have no scheduled cancellation or other update. The app keeps the existing subscription and asks Stripe to create a proration invoice with a pending update. A signed event and verified paid invoice for the requested price must arrive before the higher limits take effect. Expiration with a verified void invoice releases the pending request. The operator can use the portal for payment methods and invoice history.

## Remaining work

This slice covers first paid subscription setup and resubscription after a terminal provider state, using the current or larger plan when its limits allow. Existing paid subscribers can manage payment methods, invoices, and period-end cancellation through the portal. Deferred work includes scheduled plan changes and downgrades, overage pricing and invoicing, the full entitlement matrix, trial-end notices and dunning, cancellation export and retention lifecycle, reconciliation tooling for unmatched provider attempts, tax, and live-provider qualification. A paid subscription that ends in the sandbox projects locally as restricted to preserve historical data. The existing Growth trial starts with organization creation and requires no card. The billing screen identifies an elapsed trial while its historical entitlement stays available.

Verification uses synthetic provider responses, locally generated signatures, and disposable PostgreSQL data. No Stripe objects are created by these checks. Before enabling a sandbox, exercise the restricted-key permissions, webhook endpoint version, account separation, localized Checkout totals, portal settings, and event promotion with test-mode actors. Cover automatic payment, an upgrade invoice requiring payment, an expired update, and a delayed event after a newer invoice appears.
