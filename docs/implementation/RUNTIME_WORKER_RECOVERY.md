# Runtime worker recovery

## Worker boundaries

Cron routes retain the existing credential checks. Both the scheduled and manual workers claim jobs with a fresh invocation identifier generated by the server. The externally supplied manual run label remains in the response for operator correlation.

| Caller | Command | Persistence and evidence |
|---|---|---|
| Notification worker | `complete_notification_attempt`, `fail_notification_attempt` | Service role only. Locks the notification job and checks the current claim ID. Preserves the existing attempt result, next retry, terminal audit, provider receipt and token scrubbing in the existing notification tables and triggers. |
| Document scan worker | `complete_document_scan_attempt`, `fail_document_scan_attempt` | Service role only. Locks the scan job and checks the current claim ID before the existing digest, document and queue transitions. The existing operator command can retry a terminal scanner failure. |
| Four scheduled routes | `record_runtime_heartbeat` | Service role only. Private latest-run records preserve invocation outcome and completion time, including successful ticks with no work due. An older invocation cannot replace a newer record. |
| Platform overview | `platform_business_overview_with_runtime` | Inherits the existing platform administrator and AAL2 checks and audit. Returns worker freshness and the oldest ready queue entries, without exposing recipients or document metadata. |

Automatic recovery re-queues stale claims under the existing delay and attempt limits. An attempt that loses its claim can no longer record a result for a subsequent claim through the fenced commands. A malformed or missing mail acknowledgement is retryable with the original message idempotency key. The provider's idempotency window is finite, so externally ambiguous sends still require reconciliation. An accepted receipt is evidence of provider acknowledgment. Recipient mail-server delivery requires separate provider evidence.

A scheduled notification tick claims six messages and sends up to three at once. Two waves of 15-second relay timeouts plus reserved DB time fit inside the 60-second function budget. Monitor queue age after deployment. The scan relay uses the scanner-specific status mapping where 402 is recoverable within the existing retry bound. Apply the same mapping when integrating the homeowner branch's Cloudmersive adapter.

## Deployment order

1. Apply `20261122144012_queue_attempt_and_runtime_health.sql` to a disposable database and other approved targets before their worker deployment. The existing settlement RPC grants remain active during this step.
2. Deploy the compatible workers. Verify accepted and malformed mail receipts, reclaimed attempts, exact document digest checks, and scheduler heartbeat including a no-work tick. Verify the old worker invocations have finished or been recovered. During a mixed-version transition, old settlement RPCs retain their old behavior.
3. Apply `20261122144145_retire_unfenced_queue_settlement.sql` from the contract directory after every worker caller has switched. The fenced wrappers still use the legacy transition definitions through their owners. Run the same checks immediately after the grant change.

Before contraction, an app rollback can use the old workers against the expanded schema. After contraction, only builds using fenced settlement are compatible. Investigate with a compatible forward fix if the new workers fail. Confirm the deployed scheduler, provider receipts, delivery to a controlled inbox and duties under production volume separately.
