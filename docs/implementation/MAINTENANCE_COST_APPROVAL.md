# Maintenance cost approval

Existing estimates still request owner review when the amount is strictly above the configured `work_order_owner_approval_threshold_minor` or when the operator explicitly requires approval. Completion evaluates the supplied actual cost, falling back to the recorded amount or estimate. A larger actual expense, or a positive expense previously approved only as work scope, requires an approval round for the uncovered amount. Zero-cost work remains eligible for completion under the existing approval and completion-evidence rules.

An approval round records each active property owner entity effective on the review date. Every recipient must approve in the same round, with an approved amount at least as large as the expense and matching currency. A pending round with an outdated ownership roster requires a new request. A fully approved round still authorizes costs within its recorded amount and currency after a later transfer. A rejection or cancellation retires remaining open requests. Earlier decisions, amounts, and audits remain available in the existing authorized history.

Finance can submit or resubmit an invoice for review from a completed or closed work order. The maintenance team can request review again while completion is awaiting approval, including after a rejection or ownership change. The versioned `POST /api/v1/work-orders/{workOrderId}/cost-approval` command accepts the amount, currency, work order version, optional memo, and an idempotency key. An approval receipt confirms the review state. An invoice correction during a pending round replaces that round so the owners receive the updated amount. Finance posts separately after approval. Posting checks the exact amount and book currency with the work order locked and writes the approval round into the journal metadata for covered costs. It still permits one balanced expense and payable per work order. Existing journal entries stay immutable.

Apply migration `20261122145120_enforce_maintenance_cost_approval.sql` before deploying the application. The migration retains the existing completion, owner decision, and posting RPC signatures. Run the embedded migration and maintenance fixtures, then rehearse a blocked above-threshold completion, a closed-work-order invoice request, an owner decision, and a balanced posting in a connected staging environment. If the application is rolled back, keep the migration in place so posting remains guarded. The new request control becomes available again on application redeploy.

## In-house work

Choose **In-house team** when creating the work order. On the draft, choose **Assign in-house** to record the operator's assignment and enable scheduling. Use the existing visit, start, and completion controls. Evidence requirements and cost approval apply to in-house work. Above-threshold expenses still need the recorded owner approvals before finance can post them.

Apply migration `20261122152949_allow_in_house_work_orders.sql` before deploying the in-house controls. The existing transition RPC signature is preserved. The application can roll back with the migration in place, and previously accepted work follows the standard lifecycle.
