# Private rental application evidence

## Availability

`CRECY_RENTAL_EVIDENCE_ENABLED=1` exposes the restricted applicant and reviewer interfaces. New applications enter the private workflow only when `CRECY_RENTAL_EVIDENCE_INTAKE_ENABLED=1` is also set, the listing’s requirements are saved within its exact property’s approved policy, and the workspace is eligible. The listing editor and applications worklist show the effective mode based on the saved listing. Pausing only new intake preserves access and recovery for previously captured packets under their existing policy. The migration creates zero policies. Keep collection off until the jurisdiction, request categories, notice, review and disposition workflow, and retention schedule have been approved.

The initial application records the exact published requirement version even with the gate off. Restricted review only applies to applications that captured an eligible policy on intake. An operator changing the listing does not overwrite the applicant’s saved criteria. Before submitting a packet, the applicant acknowledges any change against the current listing version while the original requirements remain in effect.

## Applicant and reviewer access

Applicants verify contact by email, use a confirmed account with recent TOTP, and explicitly link the original verified application capability to the account. The renter accepts a versioned evidence-sharing notice specific to the policy. The account can resume drafts from an authorized device. Allowlisted, renter-supplied files and an optional self-reported score remain a separate restricted packet. The score is unverified. Applicants can supply an optional source category and observed date with their score. The workflow does not request a credit pull or calculate a score.

Reviewers need a fresh TOTP challenge, the current selected workspace, active permission for the exact property, and the case’s designated reviewer assignment. The reviewer receives only the submitted packet and can request a correction or select an applicant after verifying the required checklist. Selecting a packet is a human decision and permits the existing separate lease preparation action. It does not send a lease or activate a tenancy. An unfavorable decision involving credit material is gated on an approved notice process. Acceptable alternatives remain under the reviewed policy.

The renter and landlord see distinct stages for documents needed, submitted for review, changes requested, selected, and lease preparation. The applicant status page uses the same exact-case, unexpired verification capability. After close or decline it exposes only the reference, listing title, and disposition. Recovery and document access remain limited to active cases.

A permitted non-credit decline closes the application through the existing lifecycle command, queues one generic closure notice, and starts the policy’s retention period. The packet retains its decline as an outcome. The credit gate also covers credit material that was available before replacement or purge.

## Storage and cleanup

Use the private `private-rental-evidence` bucket. A signed-in applicant may create one opaque, immutable object at the path issued by their current grant. Clients cannot list, replace, or fetch evidence directly. The app verifies size, file signature and exact SHA-256 before finalizing the upload. A fenced scheduled worker only uses the approved Vercel Sandbox scanner snapshot. It never falls back to generic relay or credit-processing providers. The isolated verdict must attest to the exact bytes; only a clean, currently authorized file is downloadable through the app. Download responses do not cache and do not return a shareable Storage URL.

Withdrawal, conversion, closure, and policy disablement remove interactive access. Terminal schedules and removed/expired upload grants become eligible for a bounded purge. A hold blocks purge selection. Object deletion must succeed before the file digest is cleared and its tombstone recorded. `CRECY_RENTAL_EVIDENCE_PURGE_ENABLED=1` keeps that cleanup running if new collection is disabled after launch. The retry schedule and legal-hold change procedure must be proven in the deployment environment. External backups, handoffs and evidence export require their own retention and authorization rules.

## Acceptance

Use synthetic identity and financial files. Verify cross-application and cross-workspace denial, stale TOTP, applicant recovery, late and duplicate uploads, modified bytes, pending/rejected verdicts, worker retry, reviewer correction and replay, legal-hold and terminal purge. Also verify actual account confirmation on the rentals hostname and scheduled Storage plus scanner behavior before enabling a policy with any real files.

### Hosted fictional intake rehearsal

1. Verify the target project and migration versions. Use a protected candidate against the existing Supabase project, with verified Auth return URLs and test mail delivery on its rentals hostname. Enable both evidence flags only on the candidate. Confirm the production intake flag and production policy set remain off.
2. Create a new synthetic organization, property, unit, and unlisted listing through the existing operator flow. Save a narrow document checklist on that listing. Record the exact IDs. Use controlled test accounts for the active reviewer and applicant. Stop if any anchor belongs to a real property or if the candidate cannot isolate intake from public traffic.
3. Through the authorized database administrative route, create one policy in `private.rental_application_evidence_policies` for the synthetic property and organization only. Use the exact active reviewer, purpose-limited allowed categories, a synthetic notice version and text, a reference marked **synthetic QA only**, and a short retention period. Use `approved_at` and `enabled` on this test row to exercise policy checks. This fixture represents test approval only and cannot approve real collection. Never add policy approval controls to the listing editor.
4. From a clean browser, apply against the exact unlisted test link. Verify mail, account confirmation, recent MFA, and authorization with the controlled accounts. Upload sample PDFs marked **SYNTHETIC TEST**, submit, request a replacement, and confirm the review states. Verify the scanner actually settled those object versions and that a different applicant and property cannot read them.
5. Before cleanup, pause new intake on the candidate and submit a separate contact-only fixture. Confirm the original private packet remains accessible to its authorized applicant and the second application has no packet. End only the recorded fixture cases, run the approved purge on their exact objects, and verify the objects are gone and the test policy is disabled. Retain synthetic sign-in accounts only if needed for the next rehearsal. Record observed mail timing and scanner/verdict evidence with no contact addresses, tokens, or documents in the launch report.
